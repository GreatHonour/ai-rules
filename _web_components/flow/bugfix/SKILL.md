# Bug 修复 (Bugfix)

用户报告异常行为 → 复现 → 根因分析 → **输出修复计划** → 用户确认 → 回归测试 → 最小修复 → 影响范围验证 → 更新 log。

独立入口，不经过 brainstorm / plans 流程。

产物路径：`.docs/[文件名]/[YYYY-MM-DD]/[问题简述]-fix.md`（修复计划）。

---

## 触发条件

用户表述包含以下意图时触发：
- "我发现了x个 bug / 需要新增x个属性"
- "这个功能不对 / 有 bug / 有问题"
- "之前好的，现在不行了"
- 任何描述预期与实际不符的场景

---

## Phase 1：复现 & 定位

### 规则

1. 先确认复现路径：问清 **操作步骤 → 预期结果 → 实际结果**（用户已说清则跳过）
2. 查 git log 定位可疑提交：`git log --oneline -20 -- [相关文件/目录]`
3. 查 git blame 锁定具体行：`git blame [文件] -L [行范围]`
4. 判断类型：
   - **回归**：某次提交引入，之前正常 → 记录引入提交 hash
   - **原始缺陷**：从未正确处理该场景 → 记录遗漏的边界

---

## Phase 2：输出修复计划

Phase 1 分析完成后，**必须先输出修复计划，等用户确认再开始修复**。

### 输出模板

将修复计划写入 `.docs/[文件名]/[YYYY-MM-DD]/[问题简述]-fix.md`：

```markdown
# [问题简述] 修复计划

## 问题定位

**复现路径**：[操作步骤]
**预期**：[应该发生什么]
**实际**：[实际发生什么]

**类型**：回归 / 原始缺陷
**引入点**：[commit hash + 概述] / 从未实现
**根因**：[一句话描述核心原因]

## 涉及文件

| 文件 | 问题 | 修改方向 |
|------|------|----------|
| [路径] | [该文件的问题] | [怎么改] |

## 修复策略

1. [具体步骤 1]
2. [具体步骤 2]
3. ...

## 回归测试计划

- 测试文件：[路径]
- 测试场景：[描述复现 bug 的测试用例]

## 影响范围

- [列出可能受影响的模块/组件]
- 验证方式：[运行哪些测试]
```

### 规则

1. 修复计划必须具体到文件和改法，不写"待定"
2. 输出后询问用户确认，用户说"开始" / "可以" / "没问题"后才进入 Phase 3
3. 如果用户对方案有异议，调整后重新输出

---

## Phase 3：回归测试（红灯）

### 规则

1. 在相关测试文件中编写能精确复现 bug 的测试用例
2. 测试命名清晰描述 bug 场景，例：`it('连续滚动时边界坐标应同步更新')`
3. 运行测试确认红灯（当前代码下失败）
4. 如果测试直接通过 → 复现路径有误，回到 Phase 1 重新定位

### 执行

```
1. 根据根因编写最小复现测试
2. 运行：pnpm vitest run [测试文件路径]
3. 确认失败 → 继续
4. 如果通过 → 重新分析根因
```

---

## Phase 4：最小修复 & 验证

### 规则

1. 只改必要的代码，不顺手重构无关部分
2. 修复后**先验证 bug 是否修复**（Phase 3 的红灯用例变绿）
3. lint / type-check 必须通过

### 执行

```
1. 修改代码
2. 运行 bug 复现用例，确认绿灯：pnpm vitest run [bug测试文件路径]
3. 如果仍红 → 修复不完整，继续调整
4. 运行 lint（仅修改过的文件）：pnpm eslint [修改的文件列表]
5. 运行类型检查：pnpm exec vue-tsc --noEmit（如可用）
```

---

## Phase 5：TDD 用例回归

### 规则

1. 通过 `git diff --name-only` 获取本次修改的文件列表
2. 查找这些文件对应的 TDD 测试用例（同目录 `__tests__/` 或相关测试文件）
3. 运行修改文件关联的所有 TDD 用例，确认无副作用
4. 如果修改的是公共工具函数（被多处引用），扩大回归范围

### 执行

```
1. 获取修改文件：git diff --name-only HEAD
2. 定位关联测试文件：查找修改文件同级或上级的 __tests__/ 目录
3. 运行关联测试：pnpm vitest run [关联测试文件1] [关联测试文件2] ...
4. 全部通过 → 继续
5. 有失败 → 分析是修复引入的副作用还是已有问题：
   - 修复引入 → 调整修复方案，回到 Phase 4
   - 已有问题 → 记录到 log，不阻塞当前修复
```

---

## Phase 6：提交 & 更新日志

### 同步回更设计文档

修复涉及以下情况时，同步更新对应文档：

- 修改了 design.md 里描述的行为、边界或字段 → **本迭代 design.md 尚未归档**：直接同步更新（可在底部加「本迭代内修订」小节记录）；**已归档到历史日期目录**：不改历史 design，在 log.md「后续修改」小节新增条目并链回本次 fix.md
- 修复引入了新的实现细节值得追溯 → log.md「后续修改」小节链回 fix.md 路径
- 修复只是代码内部调整、不影响设计描述 → 不改 design，log.md 简述即可

fix.md 本身**保留**（根因/复现/方案是长期知识资产），不删除。

### 提交规范

```bash
git add [修改的文件]
git commit -m "fix([组件名]): [一句话描述修复内容]"
```

如果是回归，commit message 中标注：

```bash
git commit -m "fix([组件名]): [修复内容]

Regression from [引入 commit hash]"
```


## 失败处理

```
修复后测试仍红 → 重新分析根因（第 1 次）
仍然失败       → 扩大分析范围，检查上下游依赖（第 2 次）
仍然失败       → 停止，报告：
  - bug 描述和复现路径
  - 两次修复思路及失败原因
  - 建议的下一步（可能需要设计变更）
```

重试上限 2 次，超过则需用户介入或转入 plans 流程重新设计。

## 执行
修复提交与日志更新完成后，默认直接调用 `e2e/SKILL.md` 继续，无需等待用户确认。

满足以下全部条件的低风险小修复可跳过 E2E，直接进入归档，并在归档摘要中写明豁免依据：

1. 仅修改局部静态样式或 class，不改变公开 API、业务状态、交互流程、异步时序或无障碍语义。
2. 已有精确复现问题的定向回归测试，且相关测试、lint、TypeScript 检查全部通过。
3. 用户已明确完成人工验收并确认结果正常。
4. 不涉及响应式断点、浮层定位、跨组件联动或必须依赖真实浏览器才能证明的行为。

任一条件不满足时仍必须执行 E2E；不得仅凭“改动行数少”判定为小修复。
