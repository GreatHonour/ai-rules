# 代码审查 (Review)

实现完成后，对代码进行审查。先输出分级问题清单供用户确认，确认后逐一修复。

review.md 是**过程性草稿**，不是归档产物：作为用户确认清单存在，全部修复/撤回/跳过后由 archive 阶段清理，净结论合并入 log.md。

## 规则

1. 先列后修：先输出完整问题清单，用户确认后再改代码
2. 经验驱动：每次审查必须读取 `.agents/rules/code-quality.md`，逐条对照检查
3. 规范对齐：对测试文件提建议前必须先读 `.agents/rules/testing.md`，对命名/样式提建议前先读对应 rules 文件；与项目规范冲突的建议不得输出
4. 不加料：只修用户确认的问题，不顺手重构无关代码
5. 修复不引入新失败：修复后已有测试必须仍然通过
6. 审查范围仅限本次实现，不扩散
7. review.md 为过程草稿：本 skill 不做"归档"式追加；净结论由 archive skill 合并入 log.md 后删除本文件

## 审查维度

| # | 维度 | 关注点 |
|---|------|--------|
| 1 | 正确性 | 逻辑是否与 design 功能点一致 |
| 2 | 边界处理 | design 中定义的边界是否都覆盖 |
| 3 | 异常处理 | 错误状态、空值、极端输入兜底 |
| 4 | 可读性 | 命名表意、结构清晰 |
| 5 | 性能 | 只关注明显问题（不必要渲染、内存泄漏） |
| 6 | 经验规则 | code-quality.md 中的反模式是否复现 |

## 执行流程

```
1. 读取 design.md + code-quality.md
2. 逐文件审查，按 6 个维度对照
3. 输出问题清单到 review.md（格式见下），并同步展示给用户
4. 等用户确认（全部修复 / 只修红色 / 指定编号 / 跳过）
5. 按确认列表逐一修复，每修一个跑相关测试，同步更新 review.md 中该项处理状态
6. 全部修完后运行完整测试 + lint + build，确保 review.md 每项都有明确状态（已修复 / 撤回 / 用户跳过 / 延后）
7. 完整测试若仅出现并发执行下的超时，且对应定向测试此前稳定通过，必须逐文件串行复跑失败用例：串行仍失败则按真实回归处理；串行通过则记录为资源争用，并在结论中同时保留完整测试失败数与串行复跑结果，禁止直接宣称全量测试通过
```

## 输出格式

```markdown
## 审查结果

### 🔴 必须修复

1. [文件:行号] 问题描述
   - 原因：为什么有问题
   - 建议：怎么修

### 🟡 建议修复

2. [文件:行号] 问题描述
   - 原因：...
   - 建议：...

---
请确认要修复哪些（全部 / 只修红色 / 编号如 1,2,3 / 跳过）
```

### 等级标准

| 等级 | 条件 |
|------|------|
| 🔴 必须修复 | 逻辑错误、边界遗漏、安全漏洞、经验规则中标注"禁止"的条目 |
| 🟡 建议修复 | 命名不佳、结构可优化、缺少注释、性能可改进但不影响功能 |

## 产物（过程草稿）

审查阶段生成 `.docs/[文件名]/[YYYY-MM-DD]/review.md` 作为工作清单（问题列表 + 处理状态），格式即「输出格式」章节；archive 阶段读取净结论后删除本文件。

处理状态使用四种：`已修复` / `撤回（原因）` / `用户跳过` / `延后（去向）`。全部问题必须有明确状态，不允许悬空。

## 执行
没有 🔴 必须修复，或用户确认的修复全部完成且验证通过后，询问用户是否调用 `e2e/SKILL.md`， 这个时候要提示用户，要手动切换大模型。
