# 规划 (Plans)

基于上游方案（brainstorm 输出或用户直接提供的需求），依次输出完整技术设计文档和任务列表。

目录规范请看[structure.md](../templates/structure.md)

---

## Phase 1：设计文档

### 规则

1. 一份文档覆盖全方案，不按模块拆多份
2. 具体到接口定义、数据结构、类型签名，不写"待定"或 `any`
3. 每个功能点有 `[条件/操作] → 预期结果` 验收，禁止"体验良好""功能正常"
4. 只描述做什么和怎么做，不输出实现代码
5. 设计中发现遗漏的边界，直接补充到策略表并标注（设计阶段补充）
6. 不需用户确认即可输出完整文档，除非发现方案内部矛盾需要决策

### 输出模板

```markdown
# [功能名] 设计文档

## 概述

一段话描述整体方案和目标。

## 技术方案

### 组件/模块结构

ASCII 树或列表描述层级和依赖。

### 接口定义

**Props：**
| 属性 | 类型 | 默认值 | 说明 |

**数据结构：**
（TypeScript interface）

**事件：**
| 事件名 | 参数 | 说明 |

**插槽（如有）：**
| 插槽名 | 作用域参数 | 说明 |

### 状态管理

纯受控写一句声明；有复杂内部状态时展开变量名、类型、流转路径。

## 功能点

#### F1：[功能名]
- **描述**：做什么
- **验收**：
  - [条件/操作] → 预期结果

## 边界处理策略

| 场景 | 处理 |

## 不做的事（Out of Scope）

- 不实现的内容——原因
```

## Phase 2：任务拆分

读取同目录（`.docs/[文件名]/[YYYY-MM-DD]/`）Phase 1 输出的 `design.md`，输出同目录 `task.md`。

### 规则

1. 粒度：一个 task 只做一件事，10-30 分钟可完成；超过则继续拆
2. 不单独拆纯样式 task（CSS、颜色、间距等由用户处理），但组件文档和 Demo 必须作为交付 task
3. 验收从 design 的功能点验收标准派生，不发明新场景
4. 验收条件超 5 条 → 继续拆分
5. 不写 TDD 流程指令（那是 implement skill 的事）
6. 不写运行命令（implement skill 自行推断）
7. 真机测试不写入 task：依赖真机、特定系统、外部账号或人工协作的验收不拆成 task，由用户线下自行验证；task 只覆盖当前执行环境可自动化验证的场景，线下验证项在 E2E 报告中记录未覆盖风险即可

### 分类

| 类别 | 内容 | 需要测试 |
|------|------|----------|
| 基础结构 | 类型、文件骨架、工具函数 | 否 |
| 功能实现 | 对应 design 的 F1-Fn | 是 |
| 文档与示例 | `docs/components` 文档及 `docs/examples` Demo | 视交互而定 |
| 集成验证 | 端到端验证 | 是 |

### 输出格式

```markdown
# [功能名] 任务列表

## 基础结构

#### [ ] T1: [任务名]
depends: 无
- 验收条件 1
- 验收条件 2

## 功能实现

#### [ ] T2: [任务名]
depends: T1
- [输入/场景] → [预期输出]
- [边界场景] → [预期输出]

#### [ ] T3: [任务名]
depends: T1, T2
- [输入/场景] → [预期输出]

## 集成验证

#### [ ] Tn: [任务名]
depends: all
- [端到端场景] → [预期输出]
```

集成场景必须标明入口：

- `[交互入口]`：通过 Demo 中用户可操作的按钮、输入或手势验证。
- `[公开 API]`：仅当节流等交互约束无法表达高频服务语义时，在浏览器页面上下文调用公开 API；不得导入内部实现绕过公开契约。

当前执行环境无法覆盖的场景（如真机手势、企微容器）不写入 task，E2E 报告必须记录未验证风险；禁止用桌面模拟器、单元测试或其他浏览器结果替代后宣称已覆盖。

### 格式要点

- `[ ]` 未完成，`[x]` 已完成（由 implement skill 标记）
- 每个 task 标题下紧跟 `depends:` 行，列出前置 task 编号；无依赖写 `无`；依赖全部写 `all`
- 验收只写场景和预期，格式 `[场景] → [预期]`，不写“功能正常”之类模糊表述
- 轮询间隔、节流阈值等可调数值参数，验收中以常量名加默认值表述（如 `POLL_INTERVAL（默认 2s）`），避免参数调整导致多处文档批量过时
- 基础结构验收可用陈述句（无输入输出可言时）
