# 头脑风暴（从想法到决策）

读取 `delivery.json` 和 `_shared/references/document-layout.md`。本 Skill 只负责需求与业务决策；交付仓库、分支、测试平台、测试环境和目标阶段以 `flow-v3-intake` 为输入，不在这里重新登记。

## 执行流程

需求分流 → 业务闭环 → 阻塞约束 → 方案比较 → 业务与交互边界 → 决策摘要 → `flow-v3-plans`

### 1. 需求分流

- 预期与实际不符、测试失败或边界明确的小改动 → `flow-v3-bugfix`。
- 目标、范围、规则和验收均已明确 → 复述决策并进入 `flow-v3-plans`。
- 目标明确但业务规则、方案或边界未定 → 继续本流程。
- 多个可独立交付的系统 → 拆分交付模块并明确依赖顺序。

开始时说明需求类型、已知信息和唯一关键缺口，只询问一个会改变后续方向的问题。

### 2. 梳理业务闭环

先复述：

```text
[参与者] → [触发条件] → [核心操作] → [状态变化] → [最终结果]
```

按需确认目标、参与者、入口与资格、核心规则、数据真相源、职责边界、生命周期和成功标准。没有形成可复述闭环前，不讨论具体组件或实现。

### 3. 确认阻塞约束

逐个确认会改变方案或业务契约的问题：数据一致性、权限、并发/幂等、外部平台、合规/隐私、时间和非目标。每次提供 2-3 个互斥选项、推荐值和理由；发现登记信息缺失时退回 `flow-v3-intake`。

### 4. 比较真实方案

只有状态归属、一致性模型、依赖能力、用户路径或长期成本存在实质差异时才给 2-3 个方案。每个方案写核心思路、业务链路、适用条件、收益、代价与风险，并等待用户确认；库、字段命名和局部实现不构成方案分叉。

### 5. 确认边界

方案确定后，按需求选择业务异常、数据边界、交互行为、环境兼容、可访问性、性能和风险责任中的 3-5 项。平台和环境只能使用 intake 已确认的范围；本阶段只确认业务上必须满足的行为，不生成完整测试脚本。

### 6. 输出 `decision.md`

读取 `_shared/assets/decision-template.md`，写入 `.docs/<feature-slug>/<YYYY-MM-DD>/decision.md`，至少包含：

- 目标与成功标准；
- 业务闭环；
- 选定方案与理由；
- 职责边界；
- 已确认业务规则和交互；
- 风险与待外部确认；
- Out of Scope。

未清除阻塞决策前不得进入 `flow-v3-plans` 或开始实现。
