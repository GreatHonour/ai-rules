# Bugfix

独立处理缺陷和明确的小型变更，不生成 `design.md`、`task.md`，也不经过 Implement 或 Review。

## 适用范围

- **缺陷修复**：实际行为与已有预期不一致。
- **小型变更**：目标行为、边界和验收方式均已明确，不需要新增业务、交互或架构决策。
- 仍需决定“应该如何表现”，或涉及新业务流程、公开契约、跨模块方案时，停止并转入 `brainstorm/SKILL.md` 或 `plans/SKILL.md`。
- 不按代码行数判断是否属于小型变更。

## 理解上下文

遵循[上下文获取策略](../index.md#上下文获取策略所有-skill-通用)。

1. **读取功能文档**：优先读取 `.docs/[文件名]/log.md`、相关 `design.md` 和历史 `*-fix.md`；当前迭代存在 `task.md` 或 `e2e-report.md` 时一并读取。功能文档存在时即为预期来源。
2. **读取代码与测试**：读取相关代码、测试和调用关系，对照文档确认当前行为。
3. **无功能文档场景**：老代码、第三方集成等无对应功能文档时，以代码、测试作为预期来源，并在 fix.md 的历史依据中标注”无功能文档”。
4. **处理冲突**：发现文档、测试、代码或用户描述冲突时，先说明冲突并确认，不擅自选择其中一个作为预期。
5. **缺陷修复**：需明确复现步骤、预期、实际和根因。预期由功能文档确定，git 仅作根因定位工具：先用文档、代码和测试确认实际行为；需要定位引入缺陷的改动时，用 `git log -- <相关文件>` 缩小范围，发现可疑提交后用 `git show` 核对改动，必要时使用 `git blame`。无法稳定复现时，先补充日志或断言、向用户索取环境与数据；复现或根因始终不成立，则停在输出 fix.md 之前。
6. **小型变更**：需明确目标行为、不改变的边界和验证场景，并确认与已有设计及历史修改不冲突。
7. **记录改动范围**：记录工作区已有变更和本次预计修改范围，后续验证与归档不得混入其他修改。

## 输出 fix.md

写入 `.docs/[文件名]/[YYYY-MM-DD]/[问题简述]-fix.md`：

```markdown
# [问题或变更名]

## 目标
- 类型：缺陷修复 / 小型变更
- 复现：操作 → 实际结果（仅缺陷填写）
- 目标：操作或输入 → 预期结果
- 根因：[仅缺陷填写]
- 边界：[明确不改变什么]

## 历史依据
- 功能文档：[相关 log/design/fix 或“无”]
- 代码历史：[相关 commit 及结论，未发现相关提交时写明]

## 实现
- [修改点] → [结果]

## 验证场景
- [输入或操作] → [预期结果]

## 影响范围
- [模块、调用方或页面]
```

根因必须经复现或代码证实后才能写入实现方案；尚未证实时，fix.md 的根因标注“待确认”，实现部分留空或只列待验证假设，不写具体改动。内容必须具体且能执行。输出后等待用户确认；用户调整目标或边界时先更新 `fix.md`。

## 实现与验证

1. 读取 `AGENTS.md`、相关规则和现有实现，只修改确认范围内的文件。
2. 可测试的行为先添加或调整能失败的验证，再做最小修改；静态样式、配置等无法有效自动化时使用适用检查，不伪造测试。
3. 先运行定向验证，再运行受影响测试及项目适用的 lint、类型检查或构建命令。
4. 公共方法、共享状态或公共组件发生变化时，检查调用方并扩大回归范围。
5. 根据新证据能够可靠推进时继续修复；根因不成立、范围扩大或需要新决策时停止，更新 `fix.md` 并请求用户确认或转入上游流程。
6. 不在本阶段更新 `log.md` 或执行 Git 提交，这些由 `archive/SKILL.md` 统一处理。

## 下游选择

验证通过后，向用户汇报改动范围和检查结果，并给出唯一建议加一句理由，由用户确认或改选，不列判断清单让用户自行裁决。

判断原则：改动的最终可观察行为是否已被定向验证和回归检查充分证明。

- 未被充分证明 → 建议 E2E。典型为页面交互、渲染状态、响应式、浏览器行为，或公共方法最终影响页面可观察行为。
- 已被充分证明且无对外可观察行为变化 → 建议直接归档。典型为局部样式、变量、内部逻辑。

两条边界都命中或无法判断时，默认建议 E2E 并说明理由。

供用户选择：

1. 调用 `e2e/SKILL.md`
2. 调用 `archive/SKILL.md`

用户已提前指定时直接遵循，不重复询问。选择直接归档时，在归档摘要中记录验证依据。
