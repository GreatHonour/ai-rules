# 规划 (Plans)

将 `brainstorm` 的决策摘要或用户直接提供的完整需求转换为同一目录下的 `design.md` 和 `task.md`。输出目录固定为项目根目录 `.docs/[文件名]/[YYYY-MM-DD]/`；`[文件名]` 是不含扩展名的小写英文目录标识，命名规范见 [structure.md](./template/structure.md)。

**执行流程：** Phase 1 输出 design.md → Phase 2 输出 task.md → 调用 `/flow-plan-review`

---

## Phase 1：技术设计

在项目根目录创建或更新 `.docs/[文件名]/[YYYY-MM-DD]/design.md`。

### 规则

1. **输入验证**：以已确认的决策摘要或完整需求为输入；发现缺失信息会改变业务规则、权限、交互、边界、优先级或交付范围时，停止设计并返回 `brainstorm/SKILL.md`。
2. **读取上下文**：只读取本次需求直接相关的代码、文档和规则，沿用项目已有结构、命名和工具链。
3. **设计范围**：一份 `design.md` 覆盖本次交付和全部已确认决策；规模无法在一份文档内保持清晰时，返回 `brainstorm` 拆分需求。
4. **设计内容**：写清模块职责、依赖方向、状态归属、数据流转和具体契约，不输出完整实现代码；功能点使用 `[条件/操作] → [预期结果]` 描述可观察行为。
5. **技术补充**：可由现有代码和项目约定确定的技术细节允许补充，并在具体内容后标记”设计阶段补充”；例如：`- 错误语义：沿用项目统一错误码规范（设计阶段补充）`。补充内容不得改变已确认业务决策。
6. **避免模糊**：只保留当前需求需要的章节，不为套模板创建空章节，不使用”待定”、`any`、”体验良好”或”功能正常”等模糊表达。

### 设计文档骨架

```markdown
# [文件名] 设计文档

## 目标与范围

- 目标：[本次解决什么问题]
- 成功标准：[可观察结果]
- 职责边界：[负责什么，不负责什么]

## 现状与约束

- 相关现有模块、可复用能力和项目约定
- 外部依赖、运行环境和已确认限制

## 技术方案

### 模块与职责

[ASCII 树或列表：模块、职责和依赖方向]

### 核心流程与状态

[输入/触发] → [处理] → [状态变化] → [输出/结果]

### 契约

[按需描述组件契约、API、事件、数据结构、存储或外部系统契约]

## 功能点

#### F1：[功能名]

- [条件/操作] → [预期结果]
- [关键边界] → [预期结果]

## 异常与边界

- **场景** → **处理**
- [异常场景] → [处理方式]

## 风险与外部待确认

- [风险、责任人和实施前条件；没有则写无]

## Out of Scope

- [本次明确不做的内容]
```

### 按需技术章节

根据需求选择需要的章节，未涉及则省略：

- **UI 或组件** → Props、Events、Slots、交互状态、视觉约束、可访问性
- **API 或服务** → 请求响应、错误语义、权限、限流、幂等
- **数据变更** → Schema、迁移、兼容、回滚
- **异步流程** → 状态机、超时、重试、补偿、可观测性
- **ToC 活动或交易** → 资格、时间、次数/金额、概率、库存、发放、撤销、风控
- **外部平台** → 能力探测、授权、失败降级、责任边界

## Phase 2：任务拆分

读取 Phase 1 生成的 `.docs/[文件名]/[YYYY-MM-DD]/design.md`，在同一目录输出 `.docs/[文件名]/[YYYY-MM-DD]/task.md`。

### 拆分原则

1. 一个 `Txx` 对应一个可独立说明和验证的功能边界；仅在职责不同、可独立验证或存在明确依赖时拆分，同一职责的正常、异常和禁止行为写在同一任务中。
2. 标题直接说明建立或改变的能力；内容使用 `[条件/输入] → [结果]`，结构性任务可使用明确陈述句，不增加“能做/不能做”等二级栏目。
3. `task.md` 覆盖 `design.md` 的全部功能点，不新增方案、业务规则或验收场景。
4. `depends` 只指向已定义任务且不得成环：`无` 表示可以最先开始；`T1, T3` 表示依赖指定任务的产物；`all` 仅用于最终集成验证。
5. 按实际职责分类；样式、文档、Demo、数据迁移、监控等只有属于本次交付范围时才生成任务。
6. 不写 TDD 步骤、运行命令、文件清单或实现教程，这些由 `implement` 决定。
7. 仅为 `design.md` 中的浏览器 Demo 或真实页面用户流程生成“集成验证”；场景通过用户可操作入口描述，仅交互无法表达的公开契约可标记 `[公开 API]`。

### 最小格式

所有任务初始使用 `[ ]`；普通任务由 `flow-implement/SKILL.md` 标记为 `[x]`，集成验证任务由 `flow-e2e/SKILL.md` 标记。

```markdown
# [文件名] 任务列表

## [按职责生成的分类]

#### [ ] T1: [明确任务名]
depends: 无

- [条件/输入] → [预期结果]
- [关键边界] → [预期结果]
- [禁止的兜底或越界行为] → [明确结果]

#### [ ] T2: [明确任务名]
depends: T1

- [条件/输入] → [预期结果]

<!-- 仅存在浏览器 Demo 或真实页面用户流程时添加以下章节 -->

## 集成验证

#### [ ] Tn: [完整用户流程]
depends: all

- [交互入口] [用户操作] → [用户可见结果]
```

## 执行操作

Phase 1 输出 `design.md`，Phase 2 输出 `task.md`。直接调用 `/flow-plan-review`；
