# 计划审查 (Plan Review)

审查 `flow-plans` 生成的 `design.md` 和 `task.md`，确认已批准的决策被完整、准确地转化为可执行任务。

## 前置条件

必须同时存在已确认的决策摘要或完整需求、`design.md` 和同目录的 `task.md`。缺少任一项时说明原因并停止；不得从设计反推决策或降级审查。

本 skill 不适用于不生成计划文档的 `flow-bugfix`。实现后的代码审查由 `flow-review` 负责。

## 追踪审查

从原始决策重新开始，不沿用 `flow-plans` 的结论：

1. 按语义将目标、范围、规则和关键边界临时编号为 `D1、D2...`。
2. 检查每项决策是否被 `design.md` 准确覆盖。
3. 检查设计中的功能和边界是否被 `task.md` 覆盖。
4. 反查每项任务是否有设计依据，是否新增了范围或业务规则。
5. 检查文档矛盾、不可验证描述和错误的任务依赖。
6. 识别会改变参与者、对象、状态或责任边界的模糊术语；无法从决策源确定唯一含义时列为阻塞。
7. 对可能产生两种合理结果的关键规则用具体场景反证，重点关注状态变化、生命周期、权限、并发、资金和外部依赖；结果未定义时列为阻塞，不穷举低风险场景。

只在有实际疑点时读取相关代码、规则或项目文档核实现状。能自行查明的事实不要询问用户。

每个问题必须给出可核对的依据和实际影响。纯措辞偏好、泛化担忧以及实现代码质量问题不属于本次审查。

## 输出与修正

- **阻塞**：决策断链、文档矛盾、任务越界、关键决策缺失或计划不可执行。未解决前不得实现。
- **建议**：不影响正确实施，但存在明确的维护或验证风险。无法说明风险则不报告。

无问题时只报告实际检查的决策数量和通过结论，不展开完整映射。

有问题时一次列完，按以下最小信息输出：

```text
P1 [阻塞/建议] 标题
追踪：决策 → design.md 位置 → task.md 位置或缺失
影响：具体风险
建议：修改方向
```

等待用户选择全部采用或指定问题。确认前不修改文件；确认后只修改原有 `design.md` 和 `task.md`，再重新执行完整审查，不创建审查文档。

需要新增或改变业务决策时返回 `flow-brainstorm`。阻塞项清零后自动调用 `/flow-implement`；用户明确要求停在计划阶段时除外。
