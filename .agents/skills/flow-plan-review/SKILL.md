# 计划审查 (Plan Review)

从 `design.md` 理解背景，质疑 `flow-plans` 生成的 `design.md` 和 `task.md` 的模糊性、边界和可靠性。

**执行流程：** 前置条件 → 审查内容 → 问题输出 → 等待确认 → 修正文档 → 调用 `/flow-implement`

---

## 前置条件

必须同时存在：已确认的决策、`design.md` 和同目录的 `task.md`。缺少任一项时停止，不得从设计反推决策。

---

## 审查内容

从 `design.md` 理解背景，从原始决策开始，质疑模糊性、边界和可靠性。

1. 将决策编号为 `D1、D2...`，检查 决策 → `design.md` → `task.md` 映射完整性
2. 反查 task 是否越界（引入 design 未定义的行为）
3. 追问模糊目标："完成/支持XX" 的具体标准？边界？不处理什么？
4. 状态变化：谁触发？权限？转换条件？能否回退？并发一致性？生命周期？
5. 权限检查：数据变更/敏感操作的鉴权点、失败处理、绕过风险
6. 验收可靠性：task.md 的验收能否证明正确？是否覆盖状态临界、并发、边界值、外部失败、权限边界？
7. 场景反证：用具体场景挑战设计，发现两种合理结果但决策未定义时列为 `[阻塞]`

有疑点时读代码或文档核实。能查明的不问用户。决策缺失时标注 `[决策缺失]`，澄清后继续。

---

## 问题输出

- **阻塞**：决策断链、目标模糊、边界不清、状态不完整、权限缺失、验收不可靠、文档矛盾、任务越界
- **建议**：维护或验证风险，但不阻塞实现
- **无问题**：报告决策数量和通过结论
- **有问题**：一次列完，带具体追问

```text
P1 [阻塞/建议/决策缺失] 标题
追踪：D1 → design.md:行号 → task.md:Txx
质疑：[具体场景/模糊表述] 会怎样？标准是什么？
建议：修改方向
```
---

## 修正文档

确认前不修改文件。确认后只修改 `design.md` 和 `task.md`，再重新审查。`[决策缺失]` 项澄清后直接补充到 `design.md`，必要时更新 `task.md`。阻塞项清零后自动调用 `/flow-implement`；用户要求停在计划阶段时除外。
