## 归档规则

1. 归档仅处理当前功能的同一日期迭代；历史日期目录不得改写或清理。
2. 更新功能根目录的 `log.md`；删除已经存在的 `review.md`。
3. bugfix 选择直接归档 或 archive 期间不得为了满足路径结构补建 `review.md`。

## 迭代文档收敛

读取本次迭代全部 `*-fix.md` 及已有的 `design.md`、`task.md`；
是否有`design.md`、`task.md`
- 已有：属于首次任务，将全部 fix 及 E2E 的已验证修正合并回设计和任务，更新最终规则、验收场景与完成状态；确认信息完整、引用有效后删除对应 fix。
- 没有：属于独立修复，保留 fix，不新增`design.md`、`task.md`。


## 变更记录 
- 模板路径[log-template.md](./assets/log-template.md)
- 唯一允许路径：`.docs/[文件名]/log.md`（功能目录根部）。禁止在 `.docs/[文件名]/[YYYY-MM-DD]/` 创建或更新 `log.md`。
- 文档收敛后，依据合并后的设计和任务或保留的 fix 汇总整个迭代的已验证结果；对照已有日志补漏、去重，只记录最终行为。
- 日期目录只存放本次迭代产物。按日期倒序追加；同一个日期内，最新内容插入旧内容之前。
- 只记录功能变化、关键边界、结构决策和遗留事项，不写阶段流水账，也不复述其他产物。
- 没有内容的字段省略。纯重构、命名、注释和阶段完成信息不写入 `log.md`。


## 经验记录 
- 模板路径[retro-template.md](./assets/retro-template.md)
- 读取 `.docs/retro.md`，去重后按日期倒序追加；同日最新内容在前。仅记录以下三类，有内容才写，不凑齐分类。
- **项目踩坑**：实际遇到的错误 → 造成原因 → 下次如何避免。
- **执行改进**：使用 skill、MCP、agent 时发现的问题或更优方法 → 具体改进建议。
- **业务查漏**：当前业务逻辑的遗漏、冲突或优化机会 → 补充或优化建议及预期收益。
- 每条须有本次具体错误、操作或业务场景作为依据，不复述功能变更或堆砌测试通过数。改进建议标明已验证或待验证，候选不自动转为规则或实现任务。


## git 提交

归档摘要输出后执行 git 提交。

**检查变更归属**：用 `git status` 检查变更归属，只提交本次任务相关文件。
**提交内容**： 不同模块/功能分开提交，一个 commit 只做一件事；
