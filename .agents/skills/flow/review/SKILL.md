# 代码审查 (Review)

审查本次实现，输出 `.docs/[文件名]/[YYYY-MM-DD]/review.md` 供用户确认。

## 规则

1. **确定审查范围**：根据 `task.md` 和 `git diff` 确定审查范围；对比基准为任务开始前的提交。无法确认归属的修改不审查、不修改。
2. **读取预期**：读取 `design.md`、`AGENTS.md` 和本次改动适用的项目规则，不加载无关规则。遵循[上下文获取策略](../index.md#上下文获取策略所有-skill-通用)，以功能文档为预期依据。
3. **检查行为**：检查行为是否符合设计和任务边界，以及测试是否覆盖关键行为和回归风险。
4. **检查质量**：检查结构、命名、可维护性、异常、安全、性能、兼容性和过度设计，只报告有明确证据的问题。
5. **等待确认**：先列出全部问题，再等待用户决定修复、跳过或延后；确认前不修改代码。
6. **修复验证**：只修用户确认的问题，不顺手重构。修复后重新运行相关测试；全部修复完成后运行 lint、typecheck 等项目检查。

## 执行流程

1. **确定审查范围**：读取 `task.md`，用 `git diff` 确定本次改动的文件列表；读取 `design.md` 和适用规则。
2. **审查改动**：审查改动并写入 `review.md`；没有问题时记录”未发现问题”。
3. **存在问题时**：展示给用户，等待选择：全部修复、只修必须项、指定编号、全部跳过或延后。
4. **处理问题**：按用户决定处理问题，并在 `review.md` 标记：`已修复`、`撤回（原因）`、`用户跳过` 或 `延后（去向）`。
5. **进入下游**：所有问题都有明确状态且修复验证通过后进入下游；没有问题则直接进入下游。

`review.md` 是过程清单，由 `archive/SKILL.md` 直接删除。

## 输出格式

**存在问题时：**

```markdown
# [文件名] 代码审查

## 必须修复

### R1: [问题标题]

- 位置：[文件:行号]
- 问题：[实际行为或风险]
- 原因：[判断依据]
- 建议：[修复方向]
- 状态：待确认

## 建议修复

### R2: [问题标题]

- 位置：[文件:行号]
- 问题：[可维护性或非阻塞风险]
- 原因：[判断依据]
- 建议：[修复方向]
- 状态：待确认
```

**无问题时：**

```markdown
# [文件名] 代码审查

未发现需要修复的问题。

- 审查范围：[列出审查的文件]
- 审查依据：task.md, design.md, [适用规则]
```

“必须修复”用于逻辑错误、边界遗漏、安全问题或明确违反项目禁止规则；其他有证据但不阻塞功能的问题归为“建议修复”。没有对应问题的章节省略。

## 下游

若从 `implement` 内部调用，由 `implement` 控制后续流程，review 完成后不主动路由。独立调用时：

- `task.md` 存在未完成的”集成验证”任务 → 先提示用户是否调用 `/e2e`
- 不存在”集成验证”任务 → 调用 `/archive`
