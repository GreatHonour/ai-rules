# Bugfix

**执行流程**： 理解上下文 → 输出-fix.md → 等待确认 → 实现验证 → 流转操作

---

## 理解上下文

1. **读取代码与测试**：读取相关代码、测试和调用关系，对照文档确认当前行为。
2. **无功能文档场景**：老代码、第三方集成等无对应功能文档时，以代码、测试作为预期来源。
3. **处理冲突**：发现文档、测试、代码或用户描述冲突时，先说明冲突并确认，不擅自选择其中一个作为预期。
4. **缺陷修复**：
  - 需明确复现步骤、预期、实际和根因。预期由功能文档确定，git 仅作根因定位工具，先用文档、代码和测试确认实际行为；
  - 需要定位引入缺陷的改动时，用 `git log -- <相关文件>` 缩小范围，发现可疑提交后用 `git show` 核对改动，必要时使用 `git blame`。
  - 无法在开发环境中复现时，先补充日志或断言、向用户索取环境与数据；复现或根因始终不成立，则停在输出 fix.md 之前。
  - 仅限页面级的测试、类型检查、lint 使用项目已有命令，只执行适用项。
  
5. **小型变更**：需明确目标行为、不改变的边界和验证场景，并确认与已有设计及历史修改不冲突。
6. **记录改动范围**：记录工作区已有变更和本次预计修改范围，后续验证与归档不得混入其他修改。

## 实现与验证

### 实现规则

1. 读取 `AGENTS.md`、相关规则和现有实现，只修改确认范围内的文件
2. `TDD` 可测试的行为先添加或调整能失败的验证，再做最小修改；静态样式、配置等缺乏可重复验证手段时使用适用检查，不伪造测试
3. 函数用标准 `jsdoc` 注释，变量用普通注释

### 异常处理
- 根据新证据能够可靠推进时继续修复
- 根因不成立、范围扩大或需要新决策时停止，更新 `fix.md` 并请求用户确认或转入上游流程

## 流转操作

验证通过后，向用户汇报改动范围和检查结果，并给出唯一建议加一句理由，由用户确认或改选，不列判断清单让用户自行裁决

**询问执行**

- 是否执行 `/flow-e2e` 
- 是否执行 `/flow-archive`
