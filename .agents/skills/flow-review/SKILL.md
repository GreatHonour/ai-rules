# 代码审查 (Review)

审查本次实现，输出 `.docs/[文件名]/[YYYY-MM-DD]/review.md` 供用户确认。

**执行流程：** 确定范围 → 审查代码 → 输出问题 → 等待确认 → 修复验证 → 流转操作

---

## 规则

1. **检查行为**：检查行为是否符合设计和任务边界，以及测试是否覆盖关键行为和回归风险。
2. **检查质量**：检查结构、命名、可维护性、异常、安全、性能、兼容性和过度设计，只报告有明确证据的问题。
3. **等待确认**：先列出全部问题，再等待用户决定修复、跳过或延后；确认前不修改代码。
4. **修复验证**：只修用户确认的问题，不做范围外的重构。修复后重新运行相关测试；全部修复完成后运行 lint、typecheck 等项目检查。

---

## 执行流程

1. **确定审查范围**：`task.md` 和 `git diff` 确定审查范围；对比基准为任务开始前的提交。无法确认归属的修改不审查、不修改。
2. **审查改动**：审查改动并写入 `review.md`；没有问题时不生成`review.md`。
3. **存在问题时**：展示给用户，等待选择：全部修复、只修必须项、指定编号、全部跳过或延后。
4. **处理问题**：按用户决定处理问题，并在 `review.md` 标记：`已修复`、`撤回（原因）`、`用户跳过` 或 `延后（去向）`。

---

## 输出格式

**存在问题时**： 模板路径[review-template.md](./assets/review-template.md)

"必须修复" 用于逻辑错误、边界遗漏、安全问题或明确违反项目禁止规则；其他有证据但不阻塞功能的问题归为 "建议修复"。没有对应问题的章节省略。

---

## 流转操作

**修复完成后询问用户**：

  - 是否执行 `/flow-e2e` 
  - 是否执行 `/flow-archive`
