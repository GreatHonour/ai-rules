# 头脑风暴 (从想法到决策)
- **头脑风暴阶段，不要查看无关的代码文件和规则文件** 
- **执行流程：** 需求分流 → 业务闭环 → 阻塞约束 → 方案比较 → 交互与边界 → 决策摘要 → flow-plans

---

## 通用规则

1. 先梳理业务目标、参与者、输入输出、状态变化和职责边界，再讨论页面、按钮、动画或反馈；业务规则未形成可复述闭环前，不进入交互设计。
2. 会改变范围、业务闭环、数据归属或方案选择的决策逐个推进；非阻塞边界成组询问并给出建议值。
3. 只有方案在业务效果、职责边界、状态模型、依赖或长期成本上存在实质差异时，才提供 2-3 个方案；不用 "实现简单" 等空泛措辞。
4. 阻塞问题优先提供 2-3 个互斥选项；无法合理互斥时使用开放式问题，同时给出推荐值和理由。
5. 风险和边界根据需求类型筛选，不套用固定清单；每个待确认项给出建议值和理由。
6. 涉及概率、资金、库存、隐私、权限、安全、合规或外部平台时，标记风险和责任人；需外部确认的事项不得擅自定论。
7. 不在本阶段定义完整 Props、接口字段、类型签名或任务拆分；这些属于 `flow-plans`。仅记录会改变业务契约的字段决策。
8. 未清除阻塞决策前不得进入 `flow-plans`，也不得开始实现。

---

## 需求分流

根据输入识别场景选择最短有效路径：

**场景识别与处理**：

- **用户报告预期与实际不符** → 转 `flow-bugfix/SKILL.md`
- **边界明确的变更，目标、范围和验收方式均已确定** → 转 `flow-bugfix/SKILL.md`
- **目标、范围、核心规则和边界已经明确** → 复述关键决策，用户确认后转 `flow-plans/SKILL.md`
- **目标明确但方案或业务规则未定** → 继续本流程
- **同时包含多个可独立交付的系统** → 先拆分为独立交付的功能模块并确定依赖顺序，再对首个模块继续本流程

**开始方式：** 先说明当前识别的需求类型、已知信息和最关键的缺口，只询问一个会改变后续方向的问题。

## 理业务闭环

先用简短流程复述需求，例如：

```text
[参与者] → [触发条件] → [核心操作] → [状态变化] → [最终结果]
```

按需确认以下内容：

### 按需确认维度

- **目标** → 为谁解决什么问题，主成功指标是什么
- **参与者** → 用户、运营、系统或外部服务分别做什么
- **入口与资格** → 谁能进入，何时可用，需要什么前置条件
- **核心规则** → 输入、动作、判断、结果如何闭环
- **状态与归属** → 状态由谁持有，以哪一端或哪一系统为准
- **职责边界** → 当前能力负责什么，不负责什么
- **生命周期** → 开始、结束、重置、过期、撤销和恢复规则
- **成功标准** → 哪些可观察结果证明需求成立

**迭代规则**：用户纠正后更新业务闭环；没有形成可复述的闭环前，不讨论视觉方案。

---

## 确认阻塞约束

找出会淘汰方案或改变架构的关键问题（通常 3-5 个），逐个确认。常见来源包括：

**常见来源**：
- 数据真相源和一致性要求
- 权限、资格与身份状态
- 并发、幂等、库存、金额或次数扣减
- 外部系统、运行环境与兼容范围
- 合规、隐私和人工审核责任
- 明确的交付时间、复用范围与非目标

**提问格式**： 每次提问包含问题 2-3 个互斥选项、推荐选项及理由。用户已明确的信息不重复询问。

---

## 比较真实方案

阻塞约束明确后，判断是否存在方案分叉。

**方案分叉的判断标准**：状态归属、一致性模型、依赖能力、用户体验路径、长期维护成本有实质差异。

**什么不算**：用库 A 还是库 B、UI 组件选择、字段命名。

### 存在分叉

```markdown
## 方案 A：[方案名]

**核心思路**：[一句话]
**业务链路**：[关键步骤]
**适用条件**：[什么情况下成立]
**收益**：[实质收益]
**代价与风险**：[实质代价]

## 方案 B：[方案名]

...

**推荐**：方案 X
**理由**：[结合目标和约束说明，不只比较开发成本]

请选择 A / B / C，或说明需要调整的方向。收到选择前停留在方案确认阶段，不进入边界确认。
```

### 不存在分叉

只输出推荐方案、成立条件和主要取舍，并明确说明其他做法为什么只是实现细节或不满足已确认约束。

---

## 批量确认交互与边界

用户确认方案后，按当前领域筛选相关边界（不是每个需求都需要全部检查）。先列业务边界，再列前端交互；不要把两者混在一起。

**按需检查的类别：**

- **业务异常** → 重复操作、部分成功、撤销、过期、补偿、恢复
- **数据边界** → 空值、上下限、重复数据、并发、幂等、数据真相源
- **交互行为** → 防重复点击、加载、成功/失败反馈、返回、跳转、中断恢复
- **环境兼容** → 目标终端、弱网、前后台切换、视口、外部容器能力
- **可访问性** → 键盘、焦点、语义、状态提示；仅在用户界面相关时检查
- **性能** → 数据规模、频率、资源释放；仅在存在实际风险时检查
- **风险责任**  → 业务、运营、法务、安全或外部平台待确认项

优先确认与当前需求直接相关的 3-5 项。

```markdown
已选方案 X，请批量确认：

### 业务边界

1. [问题]？
   建议：[值]。理由：[一句话]

### 交互边界

2. [问题]？
   建议：[值]。理由：[一句话]
```

用户可以回复 "全部采用建议值"，或按编号修改。新信息改变已选方案时，返回第四步重新评估，不在原方案上强行打补丁。

---

## 输出决策摘要

仅保留 `flow-plans` 需要的已确认决策，不重复完整讨论过程。

```markdown
## [文件名] 决策摘要

### 目标与成功标准

- [目标]
- [可观察的成功结果]

### 业务闭环

[参与者] → [触发] → [操作] → [状态变化] → [结果]

### 选定方案

- 方案：[名称]
- 选择理由：[与目标和约束的关系]

### 职责边界

- 负责：[内容]
- 不负责：[内容]

### 已确认业务规则

- [规则]

### 已确认交互

- [交互]

### 风险与待外部确认

- [风险或责任人；没有则写无]

### Out of Scope

- [本次明确不做的内容]
```
---

## 流转操作

满足以下条件后，直接调用 `/flow-plans`；只有用户明确要求停在方案阶段时才结束：

- 目标、参与者和业务闭环已明确
- 方案及其职责边界已确认
- 会改变方案的阻塞问题已清零
- 相关业务边界和前端交互已确认
- 风险、外部待确认项和 Out of Scope 已记录
